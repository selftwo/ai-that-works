TL;DR

BEPS (BAML Enhancement Proposals) is BoundaryML's internal design-doc platform: a readable web viewer, Slack notifications, versioned comment threads, and agent-friendly export — maintained almost entirely by coding agents, not humans. The team calls the approach "fighting slop with slop": accept messy AI-generated tooling code if the workflow produces high-quality design artifacts and eventually high-quality shipped product.

Fighting slop with slop

"We generate slop code and don't care what it does. As long as the workflow is good, we're very happy. This is what we mean by fighting slop with slop." — Vaibhav, 2026-04-28-no-vibes-design-docs

The paradox is intentional:

LayerQuality barWho maintains it
Internal tooling (BEPS app, sync CLI) Low — "pure AI slop mess" Coding agents triggered from Slack
Design docs (BEPs) High — dense examples, explicit decisions Human + Claude, reviewed by team
Shipped product (BAML language) Production — on-call quality Human-owned implementation after design gate
Boundary condition This only works when tooling is not customer-facing and the workflow is simple enough that slop can't silently corrupt the artifact you care about. The gate is: does broken tooling block good docs, or just annoy you briefly?

When to apply this vs. when not to

  • Apply: one-off CLIs, export scripts, internal dashboards, sync glue, Slack bots
  • Don't apply: auth, billing, customer data paths, anything with on-call pages
  • Hybrid: use agents to scaffold, then add deterministic checks (types, tests) on the small surface that must not drift

The workflow they actually run

1. Author locally with agents

Vaibhav edits markdown with Claude while the BEPS web app holds the canonical readable copy. He spends 50%+ of time on design docs, not typing production code.

2. Sync without caring about script quality

bep pull detects drift (e.g. readme lines removed). Claude resolves the diff. Vaibhav explicitly says he doesn't know what the Python looks like — the workflow is the product.

3. Review on the web, discuss in Slack

When a doc moves to proposed, team members read in the UI. Slack threads mirror activity. No built-in "request review from X" — they @ people in Slack.

4. Export for agent context

Two export modes:

  • All BEPs zip — cross-BEP context when designing new features
  • Single BEP export — all versions + comments baked into agent_context.md

5. Extract meetings into docs

After a design huddle, paste the full meeting transcript (Granola) into Claude and ask it to re-outline the BEP with implicit decisions made explicit — cancellation semantics, shared futures, double-await rules, etc.

6. Rewrite major revisions as v2

For complex docs, in-place editing produces incoherent patches. Create v2 and rewrite rather than patch — same reason you'd rewrite tech-debt-heavy code.

Design-doc methods (independent of BEPS)

These practices transfer even if you never deploy their platform:

Decision inventory

List implicit choices one-by-one (spawn vs async, cancellation propagation, shared state).

Prior-art subpages

Keep the main doc linear; put "why not Go ctx / AbortController" on linked pages.

Example density

Middleware BEP-style: real code for retry, timeout, circuit breaker — not "Express has this."

Chunk for one-shot impl

Four days designing threading → five implementable chunks an agent can take separately.

Post-ship reconciliation

Periodically ask an agent to diff accepted BEPs against implementation.

Linear history

No divergent branches on design truth — push-only versioning for the doc corpus.

Implement it yourself (open form)

You don't need to clone BEPS. You need the separation of concerns: human-readable review surface, agent-editable source, export bundle, notification hook, and permission to write slop glue.

Tier 0 — This week, no new app ~2–4 hours
  • Folder convention: design/ with DRAFT-*.md and PROPOSED-*.md prefixes (or YAML frontmatter status: draft|proposed|accepted)
  • Export script (agent-written): one Python/bash command that concatenates all docs + git log into agent_context.md
  • Review ritual: move to proposed only after author checklist; ping reviewers in Slack/Discord with link to rendered markdown (GitHub preview or static site)
  • Meeting → doc: paste transcript; prompt: "List implicit decisions not yet in the doc; propose v2 outline"
# Minimal export (agent can flesh this out)
find design -name '*.md' | sort | while read f; do
  echo "--- FILE: $f ---"; cat "$f"; echo
done > agent_context.md
Tier 1 — Lightweight internal viewer ~1–2 days slop
  • Static generator: md → HTML via Eleventy, VitePress, or Obsidian Publish-style export — optimize for reading, not editing
  • Comments: GitHub Discussions per doc, or Hypothesis-style inline, or a Google Doc mirror for comment phase only
  • Versions: filename suffix feature-v3.md or git tags per proposed snapshot — avoid editing old versions
  • Slack webhook: on proposed transition, post title + link + @reviewers
  • Agent sync CLI: tell Claude "make pull/push that diffs local md vs exported JSON from viewer" — do not code-review the CLI
Open-form stack examples Markdown source in git · MkDocs/VitePress for pretty read · agent_context.md export · Slack incoming webhook · optional Supabase/SQLite for comment metadata if Git feels wrong
Tier 2 — BEPS-shaped platform (if you outgrow Tier 1) Agent-maintained
  • Web app: doc list, version timeline, threaded comments, draft/proposed/accepted states
  • Export API: zip with folder tree matching BEPS export shape
  • CLI: doc pull / doc push with deterministic diff + agent-assisted merge
  • Auth: GitHub OAuth; team membership via email domain or org
  • Maintenance model: file issues to your coding agent; humans never open the web app codebase except for security

Anti-patterns & caveats

  • Slop creep: internal tools that touch production data or auth — keep those typed and tested
  • Git for everything: comment threads on long-lived design docs break down in PR diffs (they said this explicitly)
  • In-place AI edits on hard docs: produces inconsistent structure — rewrite v2 instead
  • Skipping proposed gate: team reads half-baked docs; review habit dies
  • No export path: web-only docs trap knowledge where agents can't edit
  • Documentation as source of truth for code: Vaibhav clones language repos and asks Claude how things work — docs drift; code doesn't lie

## Purpose, audience, and message

Purpose: Show a live, document driven workflow for researching, designing, planning, and implementing a complex BAML feature.

Audience: Teams using coding agents on changes that cross modules or require architectural judgment.

Message: Save decisions in durable documents, use proof work when descriptions are weak, and scale the workflow to the task instead of asking for one large implementation.

## Tactical practices

- Use tiny proof programs or learning tests when a model confidently describes behavior that can be checked at runtime. See 01:03:37 to 01:04:47.
- Keep research, design, structure, and plan documents because they carry decisions into fresh context windows. See 01:21:13 to 01:24:18.
- Approve a structured outline before allowing a long implementation loop to run. See 01:24:18 to 01:26:13.
- Make each implementation phase small enough to finish in one context window and place checks at useful boundaries. See 01:30:18 to 01:31:41.
- Split very large work across several research files, plans, and independently shippable parts. See 01:36:41 to 01:38:02.

## Failures, limits, and uncertainty

- A simple plan then implement flow can hide an architectural assumption and produce poor code on a complex change. See 01:32:33 to 01:35:47.
